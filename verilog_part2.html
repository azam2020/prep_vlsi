Chapter 2: Verilog HDL — Part 2 (Q51 to Q100)

Procedural Blocks, Blocking vs Non-Blocking, Latch Inferencing, and Synthesis Hazards

5. Procedural Blocks & Sensitivity Lists

Q51 What are the two primary procedural blocks in Verilog, and how do they differ in execution?

Answer:
• initial: Executes exactly once starting at simulation time 0. Used strictly for testbenches and initialization.
• always: Executes repeatedly in an infinite loop, triggered by the conditions in its sensitivity list. Used to model actual hardware (both combinational and sequential).

Q52 Are initial blocks synthesizable?

Answer: Generally, NO for ASICs. ASIC synthesis tools completely ignore initial blocks. However, for FPGAs (like Xilinx/Intel), initial blocks are synthesizable and are used to set the power-on values of SRAMs (BRAMs) and Flip-Flops in the bitstream.

Q53 What is the difference between always @(a, b) and always @(*)?

Answer: Both model combinational logic. always @(a, b) explicitly lists the signals that trigger the block. always @(*) implicitly includes ALL signals read inside the block on the RHS into the sensitivity list automatically. @(*) is the Verilog-2001 standard to prevent missing signals.

Q54 Tricky What happens if you miss a signal in the sensitivity list? E.g., always @(a) out = a & b;

Answer: It creates a catastrophic Simulation-Synthesis Mismatch.
• Simulation: The output will ONLY update when a changes. If b changes while a is stable, the output will improperly hold its old value (acting like a latch).
• Synthesis: The synthesis tool ignores the incomplete list and builds a perfect combinational AND gate anyway. Your silicon will not match your testbench!

Q55 Can you use an edge-trigger and a level-trigger in the same sensitivity list? E.g., always @(posedge clk or a)

Answer: NO. This is illegal for synthesis. A physical hardware element is either edge-triggered (Flip-Flop) or level-sensitive (Latch/Combinational logic). You cannot mix them.

Q56 Write the standard Verilog template for a D-Flip-Flop with an Asynchronous Active-Low Reset.
always @(posedge clk or negedge rst_n) begin
    if (!rst_n)
        q <= 1'b0;
    else
        q <= d;
end
Q57 Tricky Write the standard Verilog template for a D-Flip-Flop with a Synchronous Active-Low Reset. Notice the difference!
always @(posedge clk) begin // rst_n removed from sensitivity list!
    if (!rst_n)
        q <= 1'b0;
    else
        q <= d;
end
Concept: For a synchronous reset, the reset signal is just another data input. It only gets evaluated when the clock edge rises, hence it must NOT be in the sensitivity list.
Q58 Why does the industry overwhelmingly prefer Active-Low resets (rst_n) over Active-High resets?

Answer: Power-up stability. During device power-up, voltage levels ramp up slowly. A logic '0' (GND) is a stronger, more stable physical signal than a floating/ramping VDD. Pulling the reset to ground during power-up ensures the chip stays safely locked in reset until the power supply is completely stable.

Q59 Can a single reg variable be driven by multiple always blocks?

Answer: NO. This is a "Multiple Driver" error. If two always blocks assign values to the same reg, it creates a race condition in simulation (yielding X) and is totally un-synthesizable because you are physically short-circuiting two different gate outputs together.

Q60 What is the difference between begin...end and fork...join inside an initial block?

Answer:
• begin...end: Statements execute sequentially. Delay times accumulate.
• fork...join: Statements execute concurrently (in parallel). Delay times are absolute from the start of the block.

Q61 What happens if you nest an always block inside another always block?

Answer: It is illegal syntax. Procedural blocks cannot be nested in Verilog.

Q62 How do you generate a 100MHz clock in a Verilog testbench?

Answer: 100MHz = 10ns period. So toggle every 5ns.

reg clk;
initial clk = 0;
always #5 clk = ~clk;

6. Blocking vs Non-Blocking Assignments (The Masterclass)

Q63 What is the Golden Rule of Verilog Assignments?

Answer:
1. ALWAYS use Blocking (=) for Combinational logic (always @(*)).
2. ALWAYS use Non-Blocking (<=) for Sequential logic (always @(posedge clk)).
3. NEVER mix both in the same always block.

Q64 How exactly does a Blocking Assignment (=) execute?

Answer: It evaluates the RHS and updates the LHS immediately in the Active Region. It "blocks" the execution of the next line of code in the begin...end block until the current line is fully completed and assigned.

Q65 How exactly does a Non-Blocking Assignment (<=) execute?

Answer: It evaluates the RHS in the Active Region, but defers the update of the LHS until the NBA Region. It does not block the execution of the next line; the simulator moves to the next line immediately using the "old" values of the variables.

Q66 Tricky Whiteboard Q What hardware is generated by this code? Is it a shift register? 
always @(posedge clk) begin
    q1 = d;
    q2 = q1;
    q3 = q2;
end

Answer: NO. It generates exactly ONE Flip-Flop. Because blocking assignments update immediately, `q1` gets `d`. On the next line, `q2` gets the *new* value of `q1` (which is `d`). `q3` gets the *new* value of `q2` (which is `d`). At the end of the block, `q1`, `q2`, and `q3` all output the exact same signal `d` simultaneously.

Trap Used: Using `=` in sequential blocks collapses cascaded logic.
Q67 How do you correctly write a 3-stage Shift Register?

Answer: Use Non-Blocking assignments.

always @(posedge clk) begin
    q1 <= d;
    q2 <= q1;
    q3 <= q2;
end

Because LHS updates are deferred, `q2` samples the *old* value of `q1`, creating actual hardware stages (3 Flip-Flops connected in series).

Q68 Tricky Predict the output of a and b after one clock edge. Initial values: a=10, b=20. 
always @(posedge clk) begin
    a = b;
    b = a;
end

Answer: a = 20, b = 20. The first line executes and assigns 20 to a immediately. The second line executes, sees a is now 20, and assigns 20 to b.

Q69 Predict the output of a and b after one clock edge. Initial values: a=10, b=20. 
always @(posedge clk) begin
    a <= b;
    b <= a;
end

Answer: a = 20, b = 10. The RHS is evaluated for both lines based on old values. Then both are updated simultaneously. This safely swaps the values.

Q70 What happens if you use Non-Blocking (<=) in combinational logic? always @(*) begin a <= b & c; end

Answer: It will simulate with a one-delta-cycle delay. If you cascade multiple combinational blocks using `<=`, the logic evaluation will require multiple delta cycles to propagate, severely degrading simulator performance. However, synthesis tools will usually synthesize it correctly as combinational logic anyway. (Still, it is terrible practice).

Q71 Can you assign the same variable multiple times in a single always @(posedge clk) block using <=?

Answer: Yes. If a variable is assigned multiple times via Non-Blocking assignments in the same block, the LAST assignment textually encountered is the one that takes effect (last write wins).

Q72 What is the difference between Inter-assignment delay and Intra-assignment delay?

Answer:
• Inter-assignment: #5 a = b; (Waits 5 time units, then evaluates and assigns. Used for behavioral modeling).
• Intra-assignment: a = #5 b; (Evaluates b NOW, waits 5 time units, then updates a. Used to model hardware transport delay / propagation delay).

Q73 True or False: Blocking assignments evaluate in the Active Region, but update in the Inactive Region.

Answer: False. Blocking assignments both evaluate and update in the Active Region immediately.

Q74 Why does mixing = and <= in the same block cause simulation-synthesis mismatches?

Answer: Synthesis tools rely on standard templates. Mixing them confuses the inference engine (should it build a FF or feed a wire immediately to the next gate?). Simulation will track the event queue perfectly, but synthesis may generate unpredictable logic, leading to total mismatch.

Q75 Tricky Predict the final value of `a` in this testbench block: 
initial begin
    a = 1;
    a <= 2;
    a = 3;
end

Answer: a = 2.

Concept: 1. a = 1 executes in Active region. 2. a <= 2 evaluates in Active, schedules 2 to NBA region. 3. a = 3 executes in Active region. (a is currently 3). 4. Active region empties. Simulator moves to NBA region. 5. NBA updates `a` with the scheduled `2`. Final value is 2.

7. Latch Inferencing & Synthesis Hazards

Q76 What does it mean to "infer a latch" in synthesis?

Answer: When you write combinational logic (always @(*)) but fail to specify an output for every possible input condition, the synthesis tool assumes the output must hold its previous value. Because it is not clock-edge triggered, the tool inserts a physical Level-Sensitive Latch to hold that state.

Q77 Why are accidentally inferred latches dangerous for ASIC design?

Answer:
1. They break Static Timing Analysis (STA) tools by introducing time-borrowing and combinational loops.
2. They consume extra silicon area and power compared to standard logic gates.
3. They are highly susceptible to glitches (if the enable signal glitches, the latch catches corrupted data).

Q78 Spot the bug in this code. What will synthesize? 
always @(*) begin
    if (en)
        y = a;
end

Answer: It infers a Latch. The code does not specify what y should be if en == 0. The tool will insert a D-Latch with en as the enable pin.

Q79 How do you fix the if statement to prevent a latch?

Answer: Always include an else branch that assigns a default value to the output.

always @(*) begin
    if (en) y = a;
    else    y = 1'b0; // Fully specified! Synthesizes to an AND gate.
end
Q80 Spot the bug in this case statement: 
always @(*) begin
    case(sel)
        2'b00: y = a;
        2'b01: y = b;
    endcase
end

Answer: It infers a Latch. The 2-bit sel signal has 4 possible states (00, 01, 10, 11), but only 2 are defined. If sel is 10, the tool holds the old value of y.

Q81 How do you fix a case statement to prevent a latch?

Answer: Always include a default clause, OR assign a default value to the output at the very top of the always block.

always @(*) begin
    y = 1'b0; // Default assignment catches all missing cases safely!
    case(sel)
        2'b00: y = a;
        2'b01: y = b;
    endcase
end
Q82 Tricky Will this code infer a latch? 
always @(*) begin
    if (en) y = a;
    else    y = y;
end

Answer: YES. Assigning a variable to itself (y = y) is the exact definition of a memory element holding its previous state. Synthesis tools will build a latch.

Q83 Do missing `else` statements inside `always @(posedge clk)` infer latches?

Answer: NO. Missing else/default statements inside an edge-triggered sequential block simply tell the Flip-Flop to disable its clock-enable (CE) pin and hold its state. It infers a standard Flip-Flop with an enable pin, not a Level-Sensitive Latch.

Q84 What is a Combinational Loop, and why is it a severe design error?

Answer: A combinational loop occurs when a combinational output is fed back as an input to the same logic block without passing through a Flip-Flop (e.g., assign a = a & b;). It causes infinite oscillations (like a ring oscillator), preventing timing tools from calculating delay paths and locking up simulation engines.

Q85 What do the synthesis directives `full_case` and `parallel_case` do?

Answer:
• // synopsys full_case: Tells the synthesis tool "don't build latches for unspecified states, assume they are don't cares (X)".
• // synopsys parallel_case: Tells the tool that case conditions are mutually exclusive, so build a flat MUX instead of a priority encoder (if-else chain).

Q86 Why is using `full_case` and `parallel_case` directives heavily discouraged today?

Answer: They are essentially "lying" to the synthesis tool. They instruct the synthesizer to behave one way, while the simulator (which ignores comments) behaves another. This guarantees Simulation-Synthesis mismatches. Instead, write structurally complete Verilog code.

Q87 What does assign y = 1'bx; synthesize into?

Answer: Synthesis tools treat 1'bx (Unknown) as a "Don't Care". The tool will tie y to either VDD (1) or GND (0) depending on which choice allows it to optimize the surrounding logic to the smallest area.

Q88 What happens to unconnected input ports of an instantiated module during synthesis?

Answer: Synthesis tools will typically tie floating/unconnected inputs to logic 0 (GND), or sometimes they throw a warning/error depending on compiler strictness settings. (In simulation, they float at Z).

Q89 What happens to logic that drives an unconnected output port?

Answer: The synthesis tool identifies the logic as "dead code" (having no observable output). It will optimize away (delete) all logic gates leading up to that port to save area.

Q90 Write a code snippet that intentionally creates a simulation-synthesis mismatch using a delay.

Answer: assign #10 y = a & b;
The simulator will perfectly delay the signal by 10 time units. The synthesis tool ignores #10 completely and builds a logic gate with a delay determined purely by physical cell library physics (e.g., 0.2ns).

Q91 Can a for loop be synthesized? What is the condition?

Answer: Yes, a for loop inside an always @(*) block is synthesizable ONLY IF the loop boundaries (e.g., 0 to N) are fixed compile-time constants. The synthesis tool physically "unrolls" the loop by duplicating the combinational logic N times.

Q92 Tricky What does this synthesize to? 
always @(posedge clk) begin
    y <= ~y;
end

Answer: A T-Flip Flop (or a D-Flip Flop with its Q-bar output tied back to its D input). It acts as a divide-by-2 frequency divider.

Q93 How do you avoid latches when decoding a 32-bit instruction opcode where only 10 opcodes are valid?

Answer: Do not write 32 if-else or case branches. Simply assign the outputs to a default "Idle/Zero" state at the very first line inside the always @(*) block. Then write the 10 valid case statements. The defaults cover the remaining \(2^{32} - 10\) states.

Q94 True or False: wire can only be used for Combinational logic, and reg can only be used for Sequential logic.

Answer: FALSE. wire is indeed only combinational. However, reg can model Sequential logic (if in always @(posedge clk)) AND Combinational logic (if in always @(*)). This is the biggest misconception among beginners.

Q95 What is a Glitch in combinational logic, and how does the simulator handle it?

Answer: A glitch is a transient, unwanted pulse caused by unequal propagation delays across logic branches. A standard Verilog simulator (functional sim) without SDF (Standard Delay Format) back-annotation assumes zero delay and will NOT show glitches. You must run Post-Synthesis or Gate-Level Timing Simulation to observe them.

Q96 Why must you use assign for tri-state buffers rather than an always block?

Answer: You technically *can* use an `always` block (e.g., `y = en ? a : 1'bz;`), but structural design guidelines mandate `assign` for tri-states at the top level of pads/pins to ensure clear physical separation of logic cores from I/O boundary drivers.

Q97 In an always @(*) block, can you read a variable that you assigned earlier in the same block?

Answer: Yes. Because combinational blocks use blocking assignments (=), the update is immediate. Subsequent lines in the same block will evaluate using the freshly assigned value.

Q98 What happens if you use a wire variable on the LHS of an assignment inside an always block?

Answer: The compiler will throw a fatal Syntax Error. Only reg, integer, real, or time data types can be assigned inside procedural blocks.

Q99 Explain "Time-Borrowing" in the context of Latches.

Answer: Because a latch is transparent while enabled, if the combinational logic driving the latch is slightly too slow, the data can still arrive and pass through the latch *during* the transparent window. It "borrows" time from the next logic stage. Flip-flops have a rigid edge, so they cannot borrow time.

Q100 Tricky You compile your RTL and the synthesis tool reports: "Inferred 1 Latch". The design is a CPU pipeline. What do you do?

Answer: You stop and fix the RTL immediately. In a synchronous pipelined CPU design, a latch is considered a fatal design error. It indicates missing else/default logic in an ALU or MUX. You trace the synthesis log to the exact line number, add the default assignment, and re-synthesize.

Final Concept: A clean ASIC design synthesis log has exactly ZERO accidental latches.
